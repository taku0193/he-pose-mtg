## 2. 目的と対象範囲

90分のMTGで、異なる設計の人体姿勢推定を実際に操作し、推論速度・映像表示の遅延・推定の安定性を区別して理解する。参加者がHE研究への応用案と次の検証仮説を各1件以上持ち帰ることを目標とする。

| 区分 | 内容 |
| --- | --- |
| 必須：全員 | YOLO26n-PoseとDETRPose-Nで同一の録画動画をLinux GPU上で処理し、結果を確認する |
| 必須：全員 | Macのカメラを用いたYOLO26n-Poseの遠隔ライブ推論を操作する |
| 必須：代表環境 | TAR-ViTPoseの公式コードを基に動画推論を再現し、結果・時間文脈・制限を説明する |
| 必須：共通 | Python CLI、動画・JSONL・CSV出力、比較動画、環境記録、モデル不要の自動テスト |
| 必須：資料 | README、編集可能なPPTX、90分進行表、実演台本、チートシート、まとめテンプレート |
| 任意 | DETRPoseのライブ推論、YOLO26s切替、両モデルの並列ライブ、簡易ジェスチャー判定、単一フレームViTPoseとの追加比較 |
| 対象外 | MediaPipe再実装、再学習・大規模学習、クラウドWebサービス、新たな認証基盤、大規模GUI |

P0/P1は実装の順序を表す。TAR-ViTPoseも必須範囲に含む。任意機能は必須項目の検証後に扱う。

## 3. 実行構成

### 3.1 MacとLinuxの役割

| Mac | Linux／各人に割り当てたRTX 3090 |
| --- | --- |
| カメラ取得、映像圧縮、ライブ操作、骨格描画、表示、通信を含むアプリ内遅延の計測 | フレーム受信・復号、前処理、GPU推論、後処理、結果返送 |
| 録画動画・比較動画・資料の閲覧 | 録画動画推論、ベンチマーク、結果ファイル生成 |

Macにはカメラ・表示・通信クライアントの環境を用意し、CUDA環境はLinuxに用意する。Mac自身でのモデル推論は必須にしない。

### 3.2 接続とプロセス

- 既存のSSH設定を利用する。推論ワーカーへの通信はSSHトンネル内とし、ワーカーはLinuxのループバックアドレスで待ち受ける。
- 各人が自分のワーカーとGPUを使用する。使用GPUの実識別子と、プロセスから見えるデバイス番号を記録する。
- GPUを勝手に変更しない。明示したGPUが使えない場合は理由を表示する。
- Mac側からの終了、通信切断、タイムアウトで、そのセッションが起動したワーカーとカメラを解放する。
- モデル・依存パッケージ・重みはモデル別の環境で管理する。TARは独立環境を優先する。
- モデル環境を切り替えても、利用者が操作する共通CLIと結果形式は揃える。
- ソースの版をMac・Linux・参加者間で揃え、結果に記録する。

### 3.3 オフラインの定義

準備完了後は**インターネット接続なし**で実行できることを目標とする。遠隔GPUによるライブ推論にはMac–Linux間のネットワークとSSH接続が必要である。

SSH接続まで失われた場合は、Macに事前保存した実際の結果動画・比較表・資料でMTGを続行する。事前結果の再生であることを表示し、ライブ実行の成功とは区別する。

## 4. ライブ推論の仕様

1. Macでカメラ画像を取得し、単調増加するフレームIDとMacの単調時計による取得時刻を付ける。
2. 画像を圧縮し、フレームID・画像サイズとともにLinuxへ送る。
3. LinuxでYOLO26n-Poseを実行し、元画像座標の人物・関節情報とLinux内で測った処理時間を返す。
4. Macで**同じフレームIDの画像**に骨格を重ねて表示する。新しい画像に古い推定結果を重ねない。
5. 処理が入力に追いつかないときは未処理の古いフレームを破棄し、最新画像を優先する。破棄数を記録する。

初期実装は同時処理要求1件・待機画像最大1枚とする。JPEG圧縮を第一候補とし、取得サイズ・取得FPS・圧縮品質・推論入力サイズは設定可能にして実際の使用値を保存する。

表示する値は、実際の結果表示FPS、アプリ内遅延、モデル推論時間、アプリが把握できるフレーム破棄数とする。カメラ内部の欠落数など観測できない値は不明とする。

遅延はMacで画像を取得した直後から、推定結果の描画を終え表示APIへ渡すまでを、**同じMacの時計**で測る。LinuxとMacの絶対時刻を直接引かない。この値には通信を含むが、撮像素子の露光から画面の発光までの遅延は含まない。

切断時は表示を停止し、接続エラーを通知する。過去の画像が更新されているように見せない。`q`／Ctrl+Cで終了できること、GUIのないLinuxでも動作することを受入条件とする。

## 5. モデルごとの要件

| モデル | 実装の入口 | 必須の実証 |
| --- | --- | --- |
| YOLO26n-Pose | Ultralytics公式実装、`yolo26n-pose.pt` | 録画動画を最後まで処理し、Mac–Linux間の遠隔ライブ推論を実行 |
| DETRPose-N | 公式`inference_only`、COCO用Nモデル | 公式画像推論 → 共通動画 → 共通CLIの順に実証 |
| TAR-ViTPose | 公式`tools/inference.py`と対応する設定・公開重み | 代表環境で動画推論を実証し、結果保存と時間文脈を確認 |

YOLO26・DETRPoseはまずPyTorchで再現する。TensorRTなどへの高速化は初回の必須条件にしない。公式表のTensorRT速度をPyTorch実行で再現できるとは扱わない。

TARの人物検出器、ViTPose初期化用重み、TAR本体重みを依存モデルとして明記する。公式デモにある`yolo11x.pt`は補助の人物検出器であり、主比較モデルの変更とは区別して記録する。依存モデルの無断変更はしない。

上流コミット、設定ファイル、全チェックポイントの取得元・ファイル名・サイズ・SHA256、パッケージ版を保存する。必要な設定修正はパッチ・理由・テスト結果を残し、無修正の公式実行と区別する。

## 6. TAR-ViTPoseで追加する必須条件

2026-11-03の公式コードの静的確認で、以下を把握した。実機での成功を示すものではない。

- 既定の動画処理は5フレーム、間隔1で中心フレームを推定する。中心の前後2フレームを使うため未来画像が必要となる。[公式推論コード](https://github.com/zgspose/TARViTPose/blob/42164c2c789a5297544dd836846e509459b0f1f3/tools/inference.py)
- 既定条件では動画の冒頭・末尾に結果のないフレームが生じる。出力通番と入力動画のフレーム番号を同一視できない。[公式推論コード](https://github.com/zgspose/TARViTPose/blob/42164c2c789a5297544dd836846e509459b0f1f3/tools/inference.py)
- 上流の17枠の関節定義には`head_bottom`・`head_top`があり、COCOの左右の目と意味が異なる。[公式の関節定義](https://github.com/zgspose/TARViTPose/blob/42164c2c789a5297544dd836846e509459b0f1f3/datasets/zoo/posetrack/pose_skeleton.py)
- 上流JSONでは予測点に固定の可視性値が入り、関節座標もクロップ領域内のまま出力される箇所がある。これを信頼度や元画像座標として直接取り込めない。[公式推論コード](https://github.com/zgspose/TARViTPose/blob/42164c2c789a5297544dd836846e509459b0f1f3/tools/inference.py)
- README記載の設定パスと、実際に存在する設定ファイル名が異なる。実在設定には推論ローダーが参照する一部のキーも見当たらず、整合確認・修正が必要である。[README](https://github.com/zgspose/TARViTPose/blob/42164c2c789a5297544dd836846e509459b0f1f3/README.md)、[実在する設定](https://github.com/zgspose/TARViTPose/blob/42164c2c789a5297544dd836846e509459b0f1f3/configs/posetrack17/configTARViTPoseVitB.yaml)

したがって、実装では次を必須とする。

1. 関節の**名前と意味**を基準に対応表を作る。頭部の点を目に置き換えない。元の関節情報も保存する。
2. クロップから元画像への座標変換を行う。不明なconfidence・visibilityはnullにする。
3. 出力フレームごとに入力フレーム番号・元動画時刻・参照フレーム番号を記録する。
4. 入力に対する欠落区間を比較動画上で明示する。単純に各MP4の先頭を揃えない。
5. 窓長、参照間隔、未来フレーム数、境界処理、人物検出器を実行結果と資料に記載する。
6. 人物検出・切り出しを含む処理全体の時間と、TAR本体の推論時間を分ける。
7. TARの結果はオフライン動画推論として説明し、遠隔ライブの遅延と同列のランキングにしない。

## 7. CLIと出力の仕様

次は完成時のインターフェースであり、現在実行可能なコマンドではない。

```bash
# Linux：環境確認と録画動画推論
python -m hepose.cli doctor --model all --device cuda:0
python -m hepose.cli run --model yolo26 --input assets/sample/basic.mp4 --output outputs/yolo26 --device cuda:0
python -m hepose.cli run --model detrpose --input assets/sample/basic.mp4 --output outputs/detrpose --device cuda:0
python -m hepose.cli run --model tar-vitpose --input assets/sample/basic.mp4 --output outputs/tar-vitpose --device cuda:0

# Mac：SSH接続先とリモートのプロジェクト場所を指定してライブ起動
python -m hepose.cli live --model yolo26 --camera 0 --remote <SSH_ALIAS> --remote-root <REMOTE_PROJECT_PATH> --device cuda:0 --show-fps

# Linux：同一GPU・同一動画で順番に測定し、元動画の時刻で比較
python -m hepose.cli benchmark --models yolo26,detrpose --input assets/sample/basic.mp4 --output outputs/benchmark --device cuda:0
python -m hepose.cli compare --input-dir outputs --output outputs/comparison.mp4
```

`cuda:0`は当該プロセス内の番号を表す例。各人のGPU割当を設定したうえで使う。SSH先、プロジェクト場所、モデル環境へのパスはローカル設定で管理し、秘密鍵・パスワードはプロジェクトに保存しない。

`doctor`は依存パッケージ・重み・使用デバイス・必要ファイルを確認する。実行しただけでインストール・重み取得を始めない。Macのカメラ確認とLinuxのモデル確認を分けて報告する。

各動画推論の出力：`annotated.mp4`、`poses.jsonl`、`timings.csv`、`summary.json`、`environment.json`、`run.log`。失敗時も取得できたログと状態を保存する。ライブ実行は映像録画を明示指定とし、既定では統計とログを保存する。

比較結果：`benchmark.csv`、`report.md`、実行環境情報、`comparison.mp4`。Macへ持ち帰る手順をREADMEに含める。

## 8. 共通データ形式

| 項目 | 定義 |
| --- | --- |
| 識別 | スキーマ版、実行ID、モデルID・版、入力ID・SHA256、ソースのGitコミット |
| 時間軸 | 元動画の0始まりフレーム番号、出力通番、元動画時刻ms、その時刻の取得根拠 |
| 画像 | 元画像の幅・高さ、座標系は元画像の左上原点・ピクセル |
| 人物 | bbox、関節一覧、追跡がない場合は人物IDをnull |
| 関節 | 関節定義ID、名前、x・y、confidence、confidenceの意味、visibility |
| 時系列 | 参照入力フレーム番号、窓長・間隔、未来フレーム数、推定対象フレーム番号 |
| 計時 | 各段階・処理全体の時間、計測範囲、同期方式、計れない値はnull |
| 実行条件 | 使用GPU、バックエンド、精度型、入力サイズ、重みSHA256、補助モデル |
| 状態 | 正常、失敗、未評価を区別。正常な0人検出と推論失敗を区別する |

YOLO26・DETRPoseはCOCO17を用いる。TARは元の関節定義と、意味が一致する点だけの共通形式への対応を保存する。COCO17の枠に対応点がなければ座標・confidence等をnullにする。欠けた点をゼロ座標で有効点に見せない。

フレーム内の人物通番を、フレームをまたぐ追跡IDとして扱わない。閾値を超えたconfidenceを、そのまま「実際に見えている」というvisibilityに変換しない。

## 9. 性能測定と比較

### 9.1 測る値

- **モデル推論時間**：入力テンソルからモデル出力まで。CUDAイベント等でGPU処理の完了を考慮する。
- **録画動画の処理全体時間**：読込・復号、前処理、人物検出があればその処理、推論、後処理、描画、動画書込・結果出力を含む範囲を明記する。
- **ライブのアプリ内遅延**：第4節のMac側の同一時計による値。圧縮・通信・サーバー処理・返送・Macでの描画を含む。
- **実際の処理FPS／表示FPS**：処理・表示したフレーム数と観測時間から計算する。平均処理時間の逆数とは区別する。
- **補助項目**：mean、p50、p95、成功・失敗フレーム数、処理対象数、ウォームアップ数、GPUピークメモリ、取得可能な破棄数。

起動・モデルロード・初回応答は別記録とする。初期設定はウォームアップ20フレーム、計測100フレーム以上。短い入力を繰り返す場合は回数・状態のリセット方法を記録する。計測不能な段階を0msで埋めない。

段階時間と全体時間は計測範囲を併記し、非同期処理やI/Oのため単純な足し算が一致しない場合も説明できるようにする。

### 9.2 比較の条件

- 各人の同じGPUで、同一動画・batch=1・同一フレーム順・同等の計測回数でYOLO26とDETRPoseを**順番に**測定する。
- 参加者間でPC・GPUが違う結果は環境別の表にする。異なる環境の数値からモデルの優劣を断定しない。
- モデル標準の入力設定を優先し、サイズ・精度型・閾値・バックエンドを記録する。
- 遠隔ライブの測定ではMac・Linux・ネットワークの条件を記録する。
- TARのオフライン処理は別枠にし、補助モデルと時間窓を併記する。
- 正解データがなければ精度指標は`N/A（GTなし）`。見た目の揺れ・欠落・左右の取り違え・遮蔽後の復帰を観察する。
- 学習済みモデルの公式値と自前の実測値は、表・グラフ・説明を分ける。

最低FPSなどの数値による合否基準は原案で未定義のため、本仕様では保証値を設けない。動作・操作・測定の再現を受入条件とし、数値目標を設ける場合は対象環境とともに追加合意する。

## 10. サンプル動画と比較再生

`basic.mp4`（ゆっくりした腕上げ）、`fast.mp4`（素早い反復運動）、`multi.mp4`（2人の交差・一部遮蔽）を各10～15秒程度用意する。本人の同意を得た撮影または利用条件を確認できる素材を使う。提供者・撮影担当は準備時に決める。

全員が同じファイルを使い、出典・利用条件・解像度・FPS・フレーム数・SHA256を記録する。まずは固定フレームレートの素材を対象とする。変換した場合は元ファイルも識別し、変換条件を残す。

比較動画は元動画のフレーム番号・時刻で揃える。TARなどで結果がない区間は「未推定」と表示し、補間して推定済みに見せない。並べて再生した結果を、複数モデルが同時にライブ動作した実績とは扱わない。

## 11. 開発手順・ブランチ・テスト

仕様の合意後、実装先のGit状態・ブランチ・リモート・未コミット変更を調査する。プロジェクト名は`he-pose-mtg`。引き継ぎ先ではGitHubから専用フォルダへcloneし、そのリポジトリを作業場所とする。調査前にGit初期化や既存ブランチ変更を行わない。

| 順序 | ブランチ | 内容・統合条件 |
| --- | --- | --- |
| 1 | `chore/bootstrap` | スキーマ、アダプタ契約、CLI、動画I/O、描画、計時契約、モデル不要のテスト |
| 2 | `feat/yolo26-pose` | 公式モデルの画像・動画推論、統一出力、実動画スモークテスト |
| 2 | `feat/detrpose` | 公式画像推論、動画推論、統一出力、実動画スモークテスト |
| 2 | `feat/tar-vitpose` | 公式再現、必要な明示パッチ、関節・座標・時間軸、動画保存 |
| 3 | `feat/remote-live` | **今回追加**。SSH、Macカメラ、Linux GPUワーカー、結果返送、Mac表示、切断・終了処理 |
| 4 | `feat/benchmark` | 同一動画・同一GPUの測定、同期比較動画、レポート |
| 5 | `docs/mtg-materials` | PPTX・README・台本・進行表・チートシート・まとめ |

共通基盤をmainへ統合後、更新したmainからモデル別ブランチを作る。遠隔ライブは共通基盤とYOLO26実装の統合後に進める。モデル実装は各専用ブランチで作業し、mainへの直接実装を避ける。

各機能はTDD（失敗確認 → 最小実装 → 整理）で進め、Red/Greenの実行結果を記録する。mainへ統合する時点では共通テストとlintが通過していること。実装不要の資料修正に、形式的なテストを増やす必要はない。

モデル不要の必須テスト範囲：関節名・null・座標変換、動画入力エラー、タイムスタンプ、0人／複数人、CSV/JSONL、計時集計、TARの元フレーム対応、通信メッセージと画像サイズ検証、応答フレームIDの対応、滞留フレーム破棄、切断・終了時の資源解放。

GPU・モデル重み・ネットワークを使う試験は通常の単体テストから明確に分離し、別条件で実行する。単に`not gpu`を付けるだけで、重み取得が走る構成にはしない。

統合時の最低確認は、外部モデル不要の単体テスト、ruff、CLIのhelp表示とする。各ブランチの目的・変更・試験・実動作・制限・次の作業を`docs/pr-notes/`に保存する。破壊的なGit操作や、明示依頼のないpush・公開・外部アップロードは行わない。

## 13. 完了と代替進行の区別

| 状態 | 判定 |
| --- | --- |
| 実装完了 | 必須モデル・遠隔ライブ・統一出力・測定・テスト・資料が、対応する対象環境で実証済み |
| MTGの実施準備完了 | 各人のYOLO26／DETRPoseと遠隔ライブを事前検証し、TARと障害時の実在結果・手順を用意済み |
| 一部未完了 | 必須機能が動作しない。原因・再現コマンド・ログ・影響を記録し、未完了項目を明示 |

TARなどが動かない場合に失敗記録を提出することと、その機能を完了したことは区別する。既に実際に得られた結果を使ってMTGを進める場合は、由来・生成環境・自環境での未再現を明記する。失敗記録だけで必須モデルの実装完了とは判定しない。

カメラやSSHが不調の場合は、同一動画のGPU処理またはMacに保存済みの結果へ切り替える。録画映像の処理・既存結果の再生であることを示し、当日のライブ動作成功とは別に記録する。

最終確認：3人それぞれの実行記録、各モデルの結果、遠隔ライブ、結果形式・比較時間軸、測定条件・出典、オフライン閲覧、PPTX・台本、既知の制限、次回仮説が揃っていること。

## 14. 原案からの主要な変更・明確化

| 原案の論点 | 本仕様での整理 |
| --- | --- |
| Ubuntu＋3090を優先という一般的な環境指定 | Mac操作・SSH先Linux・各人専用3090として具体化【確認済み】 |
| 全員のハンズオンと代表PCデモの境界 | YOLO26／DETRPoseは全員、TARは代表環境【確認済み】 |
| カメラの所在・表示場所が未定義 | Mac取得・Linux推論・Mac表示【確認済み】。専用ブランチを追加 |
| 全機能をネットワークなしで実行 | インターネット不要と、SSH通信が必要な遠隔実行を区別 |
| ライブ遅延と処理時間の境界 | Macの同一時計で測るアプリ内遅延と、Linux側の推論・処理時間を分離 |
| COCO17統一でTARの意味が失われる可能性 | 元の関節名を保持し、意味が一致する点だけ対応付ける |
| TARの出力を同じ動画として先頭合わせする可能性 | 元入力フレーム番号・時刻・参照窓で整列 |
| TARのREADMEだけでは再現手順が不足 | 設定・追加重み・補助検出器・必要パッチを要件化 |
| 失敗ログによる提出とDefinition of Doneが混在 | 必須機能の実装完了、MTGの代替進行、一部未完了を区別 |
| `not gpu`だけでは外部モデルを避けられない | 単体・重みあり・ネットワークありの試験を分離 |
